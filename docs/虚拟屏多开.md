# 虚拟屏多开（会话级多屏）

> 2026-10-27 实现。改动尚未装机验证，编译与 `display.*` 单测通过。

## 1. 为什么要改

改造前 `VirtualScreenSession` 是**单例单屏**：

```kotlin
private val session = AtomicReference<Session?>()
private val viewerState = MutableStateFlow(VirtualScreenViewerState())
```

配合「owner = 会话、租约 = run」这套规则，会撞出两种事故：

1. **同会话两个 run 并存**：第一个 run 持有 `RunLease`，第二个 run 调任何 GUI 工具都被
   `prepareForRun` 拒绝 → `DISPLAY_BUSY`「虚拟屏正被其他任务使用」。
2. **跨会话**：全局只有一块屏，B 会话在 A 会话使用时必然被拒；而 `virtual_screen`
   的 `close` 分支同样要先过 `prepareForRun`，busy 时连自救都做不到。

实测证据（2026-10-27 20:47~20:48 `eta-trace`）：

```
20:47:04 vscr helper 启动 runId=run-6293e0dc… owner=conv-bd053a5c…
20:48:04 run.cancel / run.end runId=run-6293e0dc…
20:48:06 vscr helper 退出 exitCode=0
```

在这个窗口里同会话的其它 run 调 `launch_app` 全部返回 `DISPLAY_BUSY`。

## 2. 现在的模型

| 概念 | 语义 |
|---|---|
| owner | **会话 id**（`AgentRuntimeWire.RunRequest.virtualScreenOwner`，即 handoff 的 conversationId） |
| sessions | `LinkedHashMap<owner, Session>`，每个会话一块屏 |
| 租约 | 仍在 session 内，按 runId 单槽：同一会话的多个 run **仍然互斥**（有意为之，防止两路输入互踩） |
| 上限 | `MAX_SESSIONS = 2`；到上限时只回收**别的会话**里 `retireIdle()` 成功的空闲屏 |
| 焦点 | `focusedOwner`；`state`（`VirtualScreenViewerState`）只镜像焦点屏，浮窗/查看页订阅它 |
| 宿主面 | `VirtualScreenHostSurfaces` 按 `"$owner|$host"` 分槽；只有拿得到自己 Surface 的 helper 走直通，其余屏自动回落整帧 JPEG |
| 唤醒锁 | 最后一块屏关闭时才 `VirtualScreenWakeLock.release()` |

`prepareForRun(owner, runId)` 的新行为：

```kotlin
本会话有活屏 → 只走租约（同会话并发仍拒绝）
本会话没屏   → 上限内直接放行（允许新建）
到上限       → 回收别的会话的空闲屏；没有空闲的才返回 false
```

## 4. 已知限制

- **浮窗仍只有一块**：跟随最近操作的会话（`focus()`），切焦点时 Surface 会重建一次。
- **非焦点屏走整帧 JPEG**：没有自己的宿主面，画质/带宽不如焦点屏；这是刻意的降级，避免两屏抢同一块 BufferQueue。
- **上限 2 块**（`MAX_SESSIONS` 常量，尚未做成设置项）。
- **同一会话内两个 run 仍互斥**：租约单槽，第二个 run 会拿到 `DISPLAY_BUSY`。
- 唤醒锁、`AgentExecutionService` 租约、虚拟屏通知都已按屏隔离，但**尚未在真机并发验证**。

## 5. 验证步骤（装机后）

1. 两个会话各发一条会用到 GUI 工具的消息 → `dumpsys display | grep -i "Eta virtual task"` 应看到两个 display；
2. 焦点在 A 时浮窗显示 A 的画面；B 操作一次后浮窗切到 B；
3. 关掉 A（`virtual_screen action=close`）→ 只有 A 的 helper 退出，B 继续；
4. 设置页「虚拟屏幕」开关在任一屏存活期间保持禁用；
5. 两块屏同时跑时观察内存与帧率，确认没有互相抢 Surface（画面不该交错）。
